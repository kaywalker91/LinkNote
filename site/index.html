Architecture

피처 우선 + Clean Architecture

각 피처는 presentation / domain / data 세 레이어로 나뉜 독립 모듈입니다. 화면은 provider를 구독하기만 하고, 상태 변경은 전부 Notifier 안에서만 일어납니다.

예외 대신 Result<T>

비즈니스 로직은 예외를 던지지 않습니다. 모든 경로가 Result<T> record를 반환하고, 실패는 Freezed sealed class Failure로 표현됩니다. 처리하지 않은 실패 분기는 컴파일 단계에서 드러납니다.

수기 provider 0개

상태 관리는 전부 @riverpod 애노테이션 코드 생성으로만 작성했습니다. provider 타입·의존성·auto-dispose 규칙이 손으로 흔들릴 여지를 없앴습니다.

오프라인 우선

Repository가 원격 실패 시 Hive CE 캐시로 물러납니다. 목록 조회는 행 단위 try/catch로 파싱해, 한 행이 깨져도 나머지 데이터가 사라지지 않습니다.

경계를 코드로 강제

tool/check_anti_patterns.sh가 CI 분석 잡에서 함께 돌며, 한번 고친 안티패턴이 다시 들어오면 머지 전에 실패합니다. 규칙을 문서가 아니라 게이트로 고정했습니다.

Engineering

무엇을 어떻게 판단했는가

기능을 나열하는 대신, 실제로 막혔던 문제와 그때 내린 결정·검증 방법을 남깁니다. 각 사례는 저장소의 PR·ADR로 이어집니다.

Routing · P0

공유하기로 저장이 안 되던 버그 — 원인은 URL 파싱이 아니라 라우터였다

문제
YouTube에서 공유해도 링크 추가 화면이 열리지 않고 홈으로 떨어졌습니다.
진단
GoRouter redirect 안에서 공유 URL을 소비(consume)하고 있었습니다. 인증이 확정될 때 refreshListenable이 연속으로 여러 번 펄스되면서 redirect가 splash에서 반복 평가되고, 1차 통과가 값을 소비해버려 후속 통과는 null을 보고 홈으로 보냈습니다.
결정
redirect를 부수효과 없는 순수 함수로 되돌리고, 일회성 소비는 도착 화면의 post-frame으로 옮겼습니다. 몇 번 평가되든 같은 결론이 나옵니다.
검증
cold-start·warm·미인증 경로별 테스트 + 실기기 YouTube 공유 확인.
PR #67 lib/app/router/
Data Integrity

링크를 지워도 태그가 남는 문제 — 4개 계층에서 동시에 막기

문제
링크를 삭제하면 조인 행은 지워지지만 tags 행이 남아, 검색 탭에 유령 태그가 계속 보였습니다.
결정
한 곳만 고치면 기존 데이터·경쟁 상태 중 하나가 새기 때문에 네 계층에 나눠 배치했습니다 — 조회는 inner join으로 연결된 태그만, 동기화는 삭제 후 삽입이 아니라 먼저 연결하고 나중에 정리하는 순서로, DB는 AFTER DELETE 트리거로 원천 차단, UI는 provider invalidate로 즉시 갱신.
왜 순서를 바꿨나
“전체 삭제 후 재삽입”은 유지되는 태그의 조인 행까지 잠깐 지워, 새로 넣은 트리거가 그 틈에 태그를 정리해버립니다.
검증
멱등 마이그레이션 스크립트 실행 + 실기기(내부 테스트)에서 유령 태그 소멸 확인.
PR #63 scripts/migration_66_orphan_tags.sql
Scope · ADR

완성된 알림 기능을 MVP에서 걷어낸 이유

상황
알림 인박스는 DTO·매퍼·데이터소스·UseCase·화면까지 전부 구현돼 있었습니다.
발견
그런데 알림을 만드는 주체가 없었습니다. 저장소 전체에서 알림 테이블에 insert하는 코드는 0건, 서버 트리거도 없었습니다. 화면은 구조적으로 영원히 빈 상태였습니다.
결정
진입점과 라우트를 제거하고 firebase_messaging 의존성도 삭제했습니다. 쓰지 않는 기능이 설치돼 있으면 스토어 심사와 보안 검토 표면만 넓어집니다. 코드는 삭제 대신 dormant 보존 — 되돌리기 비용 대비 이득이 없다고 판단하고 ADR에 사유를 남겼습니다.
재개 조건
알림을 발생시킬 이벤트(팔로우·댓글·초대)가 먼저 구현될 때. FCM을 그 전에 붙이는 건 순서가 뒤집힌 것입니다.

UI Regression

“없어졌는지”만 확인하는 테스트는 빈 자리를 못 잡는다

문제
상단 바의 마지막 액션 버튼을 제거했더니, 컴포넌트가 56px 행을 계속 예약해 화면 위에 빈 띠가 남았습니다.
왜 안 잡혔나
findsNothing 단언은 통과합니다 — 버튼은 실제로 사라졌으니까요. 사라진 것과 그 자리가 회수된 것은 다른 조건입니다.
결정
채울 내용이 없으면 행 대신 여백만 두도록 preferredSize까지 함께 줄이고, 회귀 테스트에 좌표 단언을 넣었습니다.
검증
레이아웃 테스트 4건 + 기존 렌더 경로 불변 확인(다른 화면은 항상 액션을 가지므로 영향 없음).

Release Engineering

빌드에 박히는 값과 런타임에 읽는 값을 구분하기

문제
prod 빌드에서 로그인이 실패했습니다. 서버 주소가 placeholder 그대로였습니다.
원인
envied는 .env를 런타임에 읽지 않습니다. 코드 생성 시점에 값을 생성 파일에 굽습니다. 커밋된 placeholder가 그대로 빌드에 들어갔고, 로컬 .env를 고쳐도 재생성 전에는 반영되지 않았습니다.
결정
공개용 anon 키는 생성 파일에 커밋하도록 정책을 바꿔 함정 자체를 제거했습니다. 대신 특권 자격증명은 클라이언트에 두지 않는다는 경계를 문서화했습니다 — 난독화는 APK에서 복원 가능하므로 비밀 보호 수단이 아닙니다.
실제 방어선
Google Cloud 콘솔의 앱 서명(SHA-1) 제한과 API 화이트리스트, 과금성 API 미활성화.
환경 변수 정책 envied · flutter_secure_storage

Scope

범위와 한계

지금 어디까지 됐고 무엇을 의도적으로 하지 않았는지 그대로 적습니다.

Android — 릴리스 준비 완료

릴리스 서명, 난독화 규칙, 스토어 제출용 문서까지 마쳤고 내부 테스트 트랙을 운영 중입니다.

iOS — 미착수

코드는 크로스 플랫폼이지만 서명·심사 준비를 하지 않았습니다. 플랫폼을 하나씩 끝내는 순서를 택했습니다.

알림 · FCM — 의도적 제외

알림을 발생시킬 이벤트가 없어 MVP에서 걷어냈습니다. 사유와 재개 조건은 ADR-004에 있습니다.

컬렉션 선택 — 알려진 한계
