## 0. 이 회고의 방법론

세 모델에 준 브리프는 동일했다(22.5KB). 서로의 답을 보지 못했고, 코드베이스를 새로 탐색하지 말라고 명시했다. 질문은 6개 — Keep / Problem / 진화 평가 / 비자명한 패턴 / 리스크 / 다음 30일.

세 답이 **독립적으로 같은 지점을 짚으면 그건 개인 취향이 아니라 구조**라고 보고, **갈라지는 지점은 판단이 필요한 열린 문제**로 남겼다. 그래서 이 문서에는 "합의"와 "불일치"가 둘 다 들어 있다.

여기에 세 모델이 볼 수 없었던 것 — 커밋 타임스탬프 분포, 문서/코드 라인 비율, 세션 로그 커버리지, GitHub 브랜치 보호 실제 상태 — 을 직접 집계해 4장에 붙였다.

## 2. 여섯 개의 국면

### 1막 — 폭주 (3월 중순 ~ 4월 중순)

전체 커밋의 **64%(103개)가 4월 한 달**에 몰렸다. 4월 10~11일 이틀에 1.0.0부터 1.1.5까지 **일곱 개 버전**을 올렸다(1.1.0~1.1.5 여섯 개가 4월 11일 하루). 목업 우선(Mockup-First) 전략 — UI를 목 데이터로 전부 닫고 provider 레이어에서만 백엔드로 스왑 — 이 이 속도의 엔진이었다.

### 2막 — 동결과 Wave 리뷰 (4월 중순 ~ 4월 말, Session 23~35)

기능 개발을 멈추고 feature별 리뷰 Wave 1~5를 돌렸다. P0/P1/P2/P3 심각도로 분류해 TDD로 순차 수정, `docs/reviews/`에 보고서 8건이 쌓였다. Wave 1 보안 감사는 Claude·Codex·Gemini 3자 병렬 리뷰 + 합의 매트릭스로 진행했다.

### 3막 — Harness 멀티에이전트 (5월, Session 52~57)

Planner–Generator–Evaluator 파이프라인으로 ReadingStats 기능을 Sprint-1~3에 걸쳐 개발했다. Evaluator는 Generator의 추론을 보지 않고 코드·실행 결과만으로 독립 평가한다. Sprint-2에서 planner의 family-arg 과잉 명세로 3라운드를 소모한 뒤, 글로벌 planner에 jq Self-Validation 게이트를 신설했고 Sprint-3에서 같은 회귀가 0라운드로 차단됐다.

### 4막 — 안정화 스프린트 (Session 56)

누적된 lesson 위반을 정리하며 risk profile로 PR을 3분할했다 — #39 인프라(CI 게이트 신설) / #40 semantic(`on Exception catch` 34곳 sweep) / #41 behavior(`parseRowsTolerant<T>` 일반화). 앞 PR이 만든 게이트가 뒤 PR의 결과를 ENFORCE하는 층상 구조.

### 5막 — 출시 인프라 (6~7월)

서명 keystore, R8 규칙, Supabase RLS, 인앱 업데이트 게이트(Remote Config), 스토어 자산. 커밋 수는 급감했지만 실기기 검증 비중이 올라갔다. 43개 세션 로그 중 **22개가 실기기 검증을 언급**한다.

### 6막 — 절단과 포트폴리오화 (7월 말 ~ 8월)

7-28, 외부 AI와 "이 앱에 알림이 정말 필요한가"를 따진 뒤 알림·FCM을 MVP에서 **정식 제외**하고 코드에서 걷어냈다(ADR-004). 8월에는 이력서용 소개 사이트 `site/`를 만들어 GitHub Pages에 자동 배포했다.

### 3.2 2/3 합의

- **도구의 실제 동작을 검증하지 않고 이름을 믿었다** (agy·Codex). envied가 런타임에 `.env`를 읽지 않고 build_runner가 `.g.dart`에 값을 굽는다는 사실을 놓쳐 placeholder가 prod AAB에 그대로 박혔고, 2026-07-05 재발했다. 최종 대응은 **기존 보안 규칙 자체를 폐기**하고 공개 anon 키를 커밋 허용하는 것이었다.
- **알림 제외 결정은 옳지만 시점이 늦었다** (Codex·Grok). notification 모듈을 만들고 → 탭에서 빼고(Session 48) → 7-28에야 코드를 걷었다. 만들고 지우는 비용을 이미 지불했다.
- **iOS 미착수가 구조적 리스크** (agy·Codex). Share Intent PRD가 iOS Share Extension을 선결 과제로 올려둔 상태.

### 3.3 갈라진 지점 — 판단이 필요한 곳

| 쟁점 | Grok | agy | Codex |
|---|---|---|---|
| **Harness 파이프라인의 값어치** | ReadingStats 한 기능에 비해 **프로세스 중량 과다**. 6~8월에 재사용되지 않았으므로 "제품 개발의 기본 경로가 아니라 5월에 앞당긴 메타 투자" | 성과는 있었으나 **메타-엔지니어링 과잉** 위험 노출 | 효과 있었지만 **적용 범위가 좁았다** — format 누락 같은 저장소 기본 규칙은 못 막음 |
| **8월 `site/` 포트폴리오화** | **과했다.** Phase 7이 안 닫힌 채 서사가 밖으로 나가면 "제품은 내부테스트, 외부에는 완성된 앱"이라는 괴리 | 언급 없음 | 언급 없음 |
| **4월 1.0.0 라벨** | **부적절.** "출시 가능한 1.0"이 아니라 "리뷰 대상 스냅샷"에 버전을 붙인 것 | 초기 속도전으로 긍정 평가 | 버전 증가가 배포 진척을 나타내지 못했다고 지적 |
| **다음 30일에 iOS를 넣을 것인가** | **제외하라.** 병행 금지 원칙은 3월 CocoaPods 이후 이미 한 번 되돌린 선택 | **iOS 빌드 spike는 지금 하라.** 아키텍처가 안드로이드 중심으로 굳는 걸 막아야 | 내부테스트 피드백을 한 사이클 수렴한 **뒤에** 판단 |

> **이 세 갈래 중 iOS 항목이 실질적 결정 지점이다.** Grok/Codex는 "지금은 아니다", agy는 "빌드 가능성만이라도 지금 확인"이다. 두 입장의 차이는 *구현*이 아니라 *정찰(spike)*을 어떻게 볼 것이냐에 있다 — 병행 금지 원칙이 금지하는 것은 기능 병행 개발이지 빌드 가능성 확인은 아니다. 30일 안에 **빌드 성공 여부만 확인하고 기능 작업은 열지 않는** 절충이 원칙과 충돌하지 않는다.
>
> **다만 세 모델 모두 이 제약을 모르고 답했다** — iPhone 실기기가 없어 iOS는 시뮬레이터로만 검증 가능하다(위 환경 제약 표). 이 사실은 agy의 "지금 spike하라"를 **강화하는 동시에 축소한다.** 강화: 시뮬레이터로 확인 가능한 것(빌드·의존성·CocoaPods·플러그인 JVM/Podspec 호환)은 미룰수록 비싸지므로 지금 하는 게 맞다. 축소: **Share Extension·딥링크 cold-start·설치/서명 경로는 시뮬레이터로 검증이 성립하지 않으므로**, spike의 결론은 "iOS 된다/안 된다"가 아니라 **"실기기 없이 확인 가능한 범위는 여기까지"라는 경계 확정**이어야 한다. Phase 8 진입 판단에는 기기 확보(또는 TestFlight 협력자) 계획이 선결 조건으로 들어가야 한다.

161개 커밋을 5개월로 나누면 하루 1개지만, 실제로는 **149일 중 44일에 몰려 있고 그중 45%가 주말**이다. "5개월 프로젝트"가 아니라 **44일치 집중 작업이 5개월에 흩뿌려진 프로젝트**다.

이 분포는 3장의 여러 결론과 맞물린다. 13일 공백 뒤에 재개하면 직전 맥락은 사람 머릿속에 없다 — 그래서 세션 로그 43개와 `next-session-prompt.md`가 필요했고, 문서가 코드만큼 쌓인 것도 여기서 설명된다. 문서량은 낭비가 아니라 **간헐적 작업 리듬의 필연적 비용**이었다.

### 4.2 가장 바빴던 달에 fix가 feat를 넘었다

4월: **feat 22 vs fix 27**. 전체 기간을 봐도 feat 42 : fix 37로 거의 1:1이다.

세 모델이 모두 "품질 프로세스가 폭주 뒤에 왔다"고 지적했는데, 이 수치는 그보다 강한 이야기를 한다 — **폭주하는 동안 이미 수정이 신규 기능을 앞지르고 있었다.** Wave 동결은 4월 말의 결단이 아니라, 4월 중순부터 커밋 로그가 보내고 있던 신호를 뒤늦게 읽은 것이다.

### 4.3 코드는 손으로 쓴 것의 29%뿐이다

| 산출물 | 줄 수 | 비중 |
|---|---|---|
| 테스트 | 18,100 | 39% |
| 문서 (`docs/`+`tasks/`+루트) | 14,678 | 32% |
| lib 손코딩 | 13,381 | **29%** |
| (참고) 생성 코드 | 13,010 | — |

테스트가 제품 코드의 **1.35배**, 문서가 **1.10배**다. 그런데 실제 회귀는 공유 시트 페이로드, router 다중 펄스, 생성 코드에 구워진 환경값, UI 예약 공간 — 전부 **컴포넌트 사이의 계약**에서 났다. 양이 아니라 **어디를 덮었는가**의 문제라는 Codex의 지적이 이 비율로 뒷받침된다.

### 4.4 세션 로그는 커밋일의 61%만 덮는다

커밋이 있던 날 44일 중 세션 로그가 남은 날은 **27일 (61%)** — **17일은 기록 없이 지나갔다.** 반대로 로그는 있는데 커밋이 없는 날도 3일 있다(문서를 나중에 쓴 경우).

세션 로그 43개·`next-session-prompt.md`·CHANGELOG까지 갖춘 기록 체계가 촘촘해 보이지만, 실제 커버리지는 3분의 2에 못 미친다. 4.1의 13일 공백과 겹쳐 보면 **기록이 없는 날이 곧 맥락이 끊긴 지점**이고, 재개 비용이 가장 비싼 구간이 바로 거기다.

| 개발 기간 | 28일 (03-16 ~ 04-12) | **149일** |
| 커밋 | 69 | **161** |

### 4.6 브랜치 보호는 도입됐다 — 다만 우회 가능하다

Grok은 "브리프가 브랜치 보호 404 이후 실제 도입 여부를 말하지 않는다"며 미확인으로 남겼다. 확인 결과:

```
required_status_checks: Analyze, Test, Build (Android Dev Debug), Security Scan  (strict: true)
allow_force_pushes: false · allow_deletions: false
enforce_admins: false          ← 관리자(= 유일한 기여자)는 우회 가능
```

사전 검증에서 드러난 "보호 규칙 자체가 없음(404)"은 **같은 날 Session 22에서 생성되어 해소됐다** (세션 로그 제목: "Wave 1 픽스 구현 + Branch Protection 생성 + PR 머지"). 다만 `enforce_admins: false`이므로 게이트는 협업자용이고 1인 개발자 본인에게는 강제되지 않는다. 이건 결함이라기보다 **1인 저장소에서 게이트가 갖는 구조적 한계**이며, 5장의 재발들과도 일관된다 — format은 CI가 잡았지만 **푸시 후에야** 잡았고(로컬 게이트 부재), 릴리스 바이너리·실기기 경로·레이아웃 예약은 애초에 CI가 검사하는 대상이 아니었다.

## 5. 관통하는 하나의 원인

세 모델이 각자 다른 말로 같은 곳을 가리켰다. Grok의 표현이 가장 정확하다 — **"잘못된 프록시(proxy)를 불변조건으로 일반화했다."**

| 믿은 프록시 | 실제 불변조건 | 대가 |
|---|---|---|
| `flutter analyze` 통과 | 포맷 정합성 | CI Analyze 2회 실패 (Session 38, 52) |
| `on Exception catch` | Dart `Error`까지 포함한 예외 경계 | 34곳 재증식, DTO/cast/Hive 크래시 위험 |
| `findsNothing` | 레이아웃 공간 미예약 | 탑바 56px 빈 띠 |
| `.env` 파일 존재 | 빌드 산출물에 박힌 값 | prod 로그인 불가 2회 |
| `redirect` = 순수 함수 | 부수효과 없음 | 공유 인텐트 cold-start race |
| 골든 테스트 GREEN | 플랫폼 무관 렌더링 | macOS/Linux Skia 차이로 게이트 일시 해제 |

그리고 **효과가 난 통제는 전부 실제 불변조건을 직접 어설션한 것**이다 — `dart format --set-exit-if-changed`, `check_anti_patterns.sh` grep, Linux 골든 재생성 workflow, jq `verified_canonical_evidence` 게이트, envied 정책 폐기 후 실키 커밋 허용.

4-evaluator 하네스가 통과시킨 코드에서 format이 빠진 사례가 이 원인의 결정적 증거다. **독립 리뷰어를 몇 명 세우든, 검사하는 프록시가 틀렸으면 전부 통과한다.**

## 6. 지금의 리스크 (우선순위)

**R1 — 내부테스트에 올라간 빌드에 알려진 구멍이 열려 있다.**
public-collection 딥링크 redirect에 share-intent와 동일한 latent race가 남아 있고(PR #67 후속), 컬렉션 피커는 첫 페이지 20개만 표시하며 loadMore가 없다(PR #72→#73 승계). 3/3 합의 항목. 여기서 실패하면 "iOS 미구현"이 아니라 **"저장·분류가 안 되는 북마크 앱"**이 된다.

**R2 — 빌드타임 설정 실패는 커밋 로그에 안 드러난다.**
envied placeholder는 정책 수립 전에도, 2026-07-05 prod AAB에서도 재발했다. 대응이 규칙 자체의 폐기였으므로, 같은 클래스(flavor·R8·서명·Remote Config·인앱 업데이트 게이트)의 다음 실수는 다시 전면 로그인/업데이트 불가다. 4.1이 보여주듯 이 층의 사고는 **저커밋 달에 일어난다.**

**R3 — 714 GREEN과 포트폴리오가 "출시 완료"의 대리 신호가 되는 것.**
4.5의 문서 드리프트가 이미 그 징후다. Phase 7이 안 닫힌 상태에서 외부에는 완성된 앱으로 보이면, 다음 작업 선택이 왜곡된다. 1인 버스 팩터에서 이 괴리를 교정해 줄 사람이 없다.

## 7. 다음 30일

세 모델의 권고를 교차한 우선순위다. 1~3은 3/3 합의, 4는 2/3, 5는 자체 추가.

→ *왜 지금*: 1.1.7+15가 이미 테스터 손에 있고, 이 경로가 북마크 앱의 저장·분류 루프 그 자체다.

**2. prod AAB 릴리스 리허설을 재현 가능한 절차로 고정한다 — 설치된 산출물에서 로그인 성공까지.**
→ *왜 지금*: 같은 함정이 두 번 재발했고, 대응이 규칙 폐기였으므로 다음 실수를 막는 건 절차뿐이다. "빌드 성공"이 아니라 **"설치 후 로그인 성공"**을 릴리스 정의에 넣는다.

**3. 실기기 회귀 목록을 고정하고 반복 실행한다** — 공유 시트 저장 / cold-start 딥링크 / 링크 탭 오픈 / 검색 / 컬렉션 지정 / 삭제·태그 변경.

**4. iOS는 "시뮬레이터로 확인 가능한 범위의 경계 확정"까지만 — 기능 작업은 열지 않는다.**
→ *왜 지금*: 3.3의 갈라진 지점. 병행 금지 원칙이 금지하는 건 기능 병행이지 정찰이 아니다. **단 iPhone 실기기가 없으므로 산출물은 "iOS 된다"가 아니라 "실기기 없이 확인 가능한 것 / 불가능한 것"의 목록**이어야 한다. 후자에는 Share Extension, 딥링크 cold-start, 설치·서명 경로가 들어가며, 이는 Phase 8 진입 전 **기기 확보 또는 TestFlight 협력자 계획**을 선결 조건으로 만든다.

**5. `docs/work_performance/` 7개 문서를 갱신하거나 "2026-04-12 스냅샷"으로 명시 동결한다.** *(우선순위 최하 — 로컬 전용)*

## 8. 총평

세 모델의 총평을 그대로 옮긴다.

> **Grok** — 이 5개월의 병목은 기능 속도가 아니라, 가까운 검사로 안전하다고 선언한 뒤 같은 종류의 사고를 두 번 겪고 나서야 실제 불변조건을 CI에 올리는 학습 지연이며, 지금부터의 실패 모드는 모듈 부족이 아니라 내부테스트에 올라간 캡처·분류 경로와 빌드타임 설정이다.

> **Codex** — LinkNote의 개발 방식은 반복 실패를 문서화하는 단계에서 실행 가능한 게이트로 전환하며 성숙했지만, 현재의 성패는 기능 수나 테스트 수보다 Android 운영 환경의 경계 조건을 닫고 iOS 착수를 늦출 수 있는지에 달려 있다.

> **Antigravity** — 강력한 생산성과 도구 체인을 바탕으로 1인 개발의 물리적 한계를 훌륭히 극복해 냈으나, 미뤄둔 네이티브 의존성(iOS)과 타협해 둔 잠재적 부채들이 본격적인 상용화 단계에서 가장 큰 비용 청구서로 돌아올 것이다.

그리고 데이터가 덧붙이는 한 줄:

**이 프로젝트의 진짜 성취는 714개의 테스트가 아니라, 같은 실수를 두 번 겪은 뒤 그것을 기억이 아닌 CI 스텝으로 옮긴 다섯 번의 결정이다. 남은 과제는 그 습관을 아직 게이트가 없는 층 — 릴리스 바이너리, 실기기 경로, 그리고 자기 자신에 대한 서술 — 로 확장하는 것이다.**
