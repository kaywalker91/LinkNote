## 쉽게 읽는 개발 일지 (비개발자용)

### 오늘 한 일을 한 줄로
"이 앱에 알림 기능이 정말 필요한가"를 외부 AI(Grok)와 함께 따져본 뒤, **알림·푸시를 MVP에서 정식으로 제외**하고 앱에서 그 흔적을 걷어냈습니다.

### 왜 했나요?
알림 화면은 이미 잘 만들어져 있었지만, **거기에 알림을 넣어주는 쪽이 아무도 없었습니다.** 알림이 생기려면 "누가 내 컬렉션을 팔로우했다", "내 링크에 댓글이 달렸다" 같은 사건이 있어야 하는데, 그 기능들이 아예 만들어져 있지 않았습니다. 결과적으로 홈 화면의 종 아이콘을 누르면 **영원히 텅 빈 화면**만 나오는 상태였습니다.

게다가 LinkNote는 사용자가 필요할 때 직접 열어보는 성격의 앱(저장하고, 나중에 찾아보는 개인 서랍)이라, 앱 밖에서 먼저 말을 거는 푸시 알림과는 방향이 맞지 않았습니다. 흔히 대안으로 나오는 "저장만 하고 안 읽은 링크 알려주기"도 북마크 앱에서는 오히려 잔소리로 느껴지는 실패 패턴이라 함께 기각했습니다.

취업 포트폴리오 관점에서도 감점 요인은 "푸시가 없는 것"이 아니라 **"기획서엔 알림이 있다고 써놓고 눌러보면 빈 화면인 것"** 이었습니다. 그래서 없는 기능을 만드는 대신, 없다는 사실을 정확하게 정리하는 쪽을 택했습니다.

### 오늘 변경된 것 (쉬운 말로)
1. **홈 화면 종 아이콘 제거**: 빈 화면으로 가는 유일한 입구였던 알림 벨을 없앴습니다. 그 옆의 정렬 아이콘은 그대로 남아 상단바 모양은 변하지 않습니다.
2. **안 쓰는 푸시 라이브러리 제거**: 설치만 되어 있고 한 번도 쓰이지 않던 푸시 알림 라이브러리(`firebase_messaging`)와 딸린 패키지 2개를 걷어냈습니다. 앱이 수집하지도 않는 기능이 설치돼 있으면 스토어 심사·보안 검토에서 설명할 거리만 늘어납니다.
3. **알림 화면 코드는 지우지 않고 보관**: 잘 만들어진 코드라 통째로 삭제하는 대신, 앱에서 갈 수 없게만 막아뒀습니다. 나중에 팔로우 같은 기능을 만들면 그때 다시 꺼내 쓸 수 있습니다.
4. **결정 이유를 문서로 남김**: 왜 잘랐는지, 어떤 대안을 왜 기각했는지, **언제 다시 열지**(팔로우/댓글 같은 알림 발생 이벤트가 먼저 생길 때)를 설계 결정 문서(ADR-004)에 기록했습니다.
5. **기획서·README를 실제 앱과 일치시킴**: 문서엔 "하단 탭 5개(알림 포함)"로 적혀 있었지만 실제로는 4탭이었던 것 등, 이번에 발견한 문서-코드 불일치 3건을 함께 바로잡았습니다.
6. **세션 일지 정리**: 40개가 한 폴더에 쌓여 있던 개발 일지를 연월별 폴더로 나누고 안내 문서를 붙였습니다.

## 오늘 작업 요약

알림 기능 존치 여부를 Grok과 논의하고, 그 결과를 코드 실측으로 검증한 뒤 **F06(알림) 전체와 FCM을 MVP에서 영구 제외**하기로 결정했다.

판단 근거는 코드로 확인했다 — 리포 전체에서 `from('notifications')`는 `select`/`update(is_read)` 3곳뿐이고 **insert가 0건**이며 서버 트리거·Edge Function도 없다. PRD F06이 정의한 발생 소스(팔로우/댓글/공유 초대)에 해당하는 기능도 `lib/`에 존재하지 않아 `NotificationScreen`은 구조적으로 영구 empty state였다. `firebase_messaging`도 pubspec에만 있고 사용 0건이었다.

처리는 **"진입점만 제거, 레이어는 dormant 보존"** 최소안을 채택했다(사용자 결정). 홈 탑바 벨과 `/notifications` 라우트·상수를 제거하고 `firebase_messaging`을 걷어냈으나, `lib/features/notification/**`과 테스트는 그대로 남겼다. 빈 화면 노출이라는 실질 문제는 진입점 제거만으로 해소되고, 동작하는 코드를 지우는 것은 되돌리기 비용만 있기 때문이다.

논의 과정에서 Grok이 브리프의 사실 오류를 정정했다 — 알림은 하단 탭이 아니라 홈 AppBar 벨이었다(탭은 4개). 브리프에 PRD 문장을 그대로 인용한 것이 원인이었고, 이를 계기로 PRD·workflow·README에 누적돼 있던 문서 드리프트 3건을 함께 정리했다.

## 오늘의 학습

### 새로 배운 것
- **외부 모델 브리프의 사실은 코드에서 뽑아야 한다**: 브리프 대부분은 grep 실측으로 채웠으나 UI 구조 한 줄만 PRD 문장을 인용했고, 그게 정확히 드리프트 구간이었다(5탭 vs 4탭). Grok이 코드를 읽고 정정했다. **문서는 검증 대상이지 근거가 아니다** — 특히 문서-코드 정합 자체가 논점인 스코프 결정 작업에서는 문서 인용이 곧 오염이다. 부수 효과로, 브리프 작성 과정이 문서 드리프트 감사가 된다.
- **"기능이 있다"와 "기능이 동작한다" 사이의 간극은 쓰기 경로로 판별된다**: 알림은 읽기 경로(select/update)가 완비돼 있어 코드만 보면 완성된 기능으로 보인다. `insert` 주체를 찾는 한 번의 grep이 "완성된 기능"과 "영구 empty state"를 갈랐다. 읽기만 있는 feature는 데이터 공급자를 먼저 확인할 것.
- **범위를 자르는 결정도 산출물이다**: 잘라낸 이유·기각한 대안·재개 조건을 ADR로 남기면, 없는 기능이 "누락"이 아니라 "판단"으로 읽힌다. 이 프로젝트의 목표(포트폴리오)에서는 FCM 구현보다 이 기록이 더 강한 신호다.
